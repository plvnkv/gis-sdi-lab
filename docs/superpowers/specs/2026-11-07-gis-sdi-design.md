# Архітектура репозиторію GIS/SDI

Статус — проєкт на погодження. Дата — 2026-11-07.

## Мета й топологія

Мала команда має відтворювати платформу з GitHub та резервних копій без ручного відтворення конфігурації. Перший реліз охоплює один фізичний GIS-сервер із k3s, окремий малий вузол MAAS і NAS для копій. Відмова GIS-сервера зупиняє GIS. Ціль першого релізу — виміряне відновлення на чистому вузлі. Кластерну HA та другий постійний кластер винесено за межі першого релізу.

Погоджений варіант — MAAS region+rack на окремому вузлі. Розглянута VM на NAS зменшує кількість пристроїв за наявності підтримки PXE у мережі VM, але пов'язує доступність провіжинінгу з доступністю NAS. Окремий вузол дозволяє обслуговувати NAS і перевстановлювати GIS-сервер незалежно. MAAS має власну БД, а керування BMC ізолюється в мережі адміністрування. PXE/DHCP налаштовується на виділеному сегменті або узгоджується з чинним DHCP. Перед розгортанням перевіряються маршрут до BMC, PXE та розмітка дисків.

## Структура

Погоджено один публічний репозиторій GitHub із захищеною основною гілкою та різними власниками шляхів. Такий поділ дозволяє перевіряти зміни bootstrap і GitOps у межах одного PR.

```text
.github/
  CODEOWNERS
  workflows/              # Перевірки PR і збирання власних образів
bootstrap/
  maas/                   # Інвентар без секретів, шаблони cloud-init, розмітка
  k3s/                    # Закріплена версія та конфігурація вузла
  argocd/                 # Початковий інсталятор і точка передачі керування
clusters/
  prod/                   # Коренева Application, AppProjects, дочірні Applications
platform/
  ingress/                # Маршрути, TLS і політики доступу
  storage/                # Класи сховища, політики томів, конфігурація копій
  secrets/                # Політика та конфігурація розшифрування
  observability/          # Prometheus, Grafana, Alertmanager, Loki, Alloy
apps/
  postgis/
  rustfs/
  geonode/                # Django, Celery, GeoServer, сумісний брокер
  martin/
  titiler/
docs/
  adr/                    # Рішення, матриця версій, критерії заміни
  runbooks/               # Bootstrap, оновлення, відновлення, ротація ключів
  superpowers/specs/
```

Кожен каталог застосунку містить один явний спосіб рендерингу, Helm або Kustomize. Значення і патчі для production зберігаються поруч із застосунком, а clusters/prod визначає склад кластера та дозволені джерела й призначення. Додавання другого кластера потребує окремої точки входу в clusters/.

## Bootstrap та GitOps

1. Адміністратор реєструє вузол у MAAS, перевіряє інвентар і явно запускає розгортання Ubuntu LTS. Перевстановлення вимагає перевірки ID машини, дисків і доступності останньої копії. Merge в GitHub не запускає операції з дисками.
2. Cloud-init готує доступ і монтування дисків. Ідемпотентний bootstrap встановлює зафіксовану версію k3s та Argo CD, вказує Argo CD публічний Git URL для читання без облікових даних й застосовує кореневу Application. Пропозиція для k3s — однонодовий embedded etcd із шифруванням Kubernetes Secrets і копіями стану поза сервером. [Відновлення k3s](https://docs.k3s.io/datastore/backup-restore)
3. Argo CD керує платформою та застосунками. Коренева Application має адміністративні повноваження, тому зміни clusters/prod та bootstrap проходять рев’ю власника платформи. Дочірні AppProjects обмежують репозиторії, namespaces і типи ресурсів. Першими встановлюються CRD і контролери, далі сховища та застосунки. Готовність PostGIS, RustFS та брокера перевіряють probes і повторні спроби клієнтів. Порядок застосування маніфестів сам по собі не гарантує готовності залежностей. [Bootstrap Argo CD](https://argo-cd.readthedocs.io/en/stable/operator-manual/cluster-bootstrapping/)
4. GitHub Actions на PR рендерить усі production Applications, перевіряє схеми з CRD, політики, витоки секретів і версії артефактів. Для власних образів окремий workflow збирає їх у GHCR, а PR змінює digest у Git. CI не потребує доступу до Kubernetes API. Argo CD застосовує зміни після merge та виправляє drift. Автоматичний prune дозволяється для безстанових ресурсів. Видалення PVC, баз і бакетів та незворотні міграції мають окрему контрольовану процедуру. Відкат Git повертає конфігурацію, а відкат даних залежить від сумісності схеми або потребує відновлення з копії.
5. Пропозиція для секретів — SOPS з age і контрольованим інтеграційним плагіном Argo CD. Публічний Git містить лише безпечну для публікації конфігурацію та приклади. Конфігурація майданчика і зашифровані production-секрети надходять через окреме захищене джерело. Ключ age, облікові дані bootstrap та k3s token вводяться поза Git і зберігаються в незалежному від GIS-сервера сховищі з контрольованим аварійним доступом. Ключ розшифрування копій має бути доступний до запуску кластера.

## Компоненти й доступ

| Компонент | Початковий дизайн |
|---|---|
| PostGIS | Один екземпляр PostgreSQL з PostGIS. Окремі бази й ролі для GeoNode та просторових даних. Оператор, образ і спосіб архівації WAL підбираються разом після перевірки сумісності з GeoNode і Martin. |
| GeoNode та GeoServer | Єдина версійна матриця. Окремі процеси GeoNode web і Celery, GeoServer із сумісними розширеннями, брокер із вибраного upstream-релізу. Міграції виконуються однією повторюваною задачею. Зберігаються медіа GeoNode і GeoServer DATA_DIR, включно зі станом, створеним через портал. |
| RustFS | Робочий S3 endpoint із постійними локальними дисками. Режим дисків визначається після інвентаризації. Політики бакетів і сервісні облікові записи відокремлені. Сумісність перевіряється на реальних операціях клієнтів. |
| Martin | Читання з PostGIS через окрему роль та явний список джерел. Відкриття шару через GeoNode не змінює доступ у Martin автоматично. |
| TiTiler | Читає тестові COG із RustFS через окремі права доступу. Перед публікацією перевіряються range reads, endpoint, формат адресації бакета та поведінка при відмові доступу. Вхідний маршрут приймає дозволені ідентифікатори джерел або обмежені URL, а мережевий egress обмежується. |

Початковий профіль доступу — внутрішні маршрути з TLS. Kubernetes API, MAAS, Argo CD, адмінки GeoServer і RustFS та Grafana доступні через адміністративну мережу або VPN. Публічні маршрути, SSO та правила доступу до приватних шарів погоджуються до відкриття сервісів назовні. NetworkPolicy обмежують трафік між компонентами. GeoNode, GeoServer, Martin і TiTiler проходять перевірку на анонімний доступ до приватного тестового шару. [GeoNode](https://docs.geonode.org/projects/v4/en/4.4.x/basic/settings/index.html), [Martin](https://maplibre.org/martin/installation/), [RustFS](https://docs.rustfs.com/en/reference/s3-compatibility)

## Диски, резервування та відновлення

Постійні дані лежать на локальних томах із задокументованими шляхами та політикою Retain для критичних PV. Розміщення PostGIS, RustFS та телеметрії планується за інвентарем дисків і профілем I/O. NAS є окремим місцем резервування. Копії мають власні облікові дані, контроль цілісності й політику зберігання. Якщо NAS підтримує snapshots або immutable retention, права видалення історії відокремлюються від запису нових копій.

| Що відновлюємо | Що копіюємо |
|---|---|
| MAAS | Конфігурацію та БД MAAS, опис мережі, інструкцію доступу до облікових даних. Копія на NAS має читатися без GIS-кластера. |
| k3s | etcd snapshots та окремо захищений оригінальний серверний токен. Знімок etcd містить стан Kubernetes, а вміст PV резервується окремо. |
| PostGIS | Консистентні базові копії і WAL для PITR, якщо це потрібно за RPO. Копії перевіряються відновленням у чистий екземпляр із потрібною версією розширень. |
| RustFS | Об'єкти й потрібні метадані через перевірений механізм експорту, окремо опис бакетів, політик та відтворення сервісних облікових записів. Перевірка за контрольними сумами й читанням через TiTiler. |
| GeoNode та GeoServer | Медіа, DATA_DIR і конфігурація поза Git. Для тесту спільного відновлення зафіксувати узгоджену точку копіювання PostGIS, медіа й RustFS, наприклад короткою паузою записів і фонових задач. |
| Спостережуваність | Правила, дашборди й джерела даних відтворюються з Git. Історію метрик та логів зберігаємо окремо лише за узгодженої потреби. |

Основний сценарій після втрати сервера — MAAS розгортає чистий вузол, bootstrap відновлює доступ і Argo CD, а дозволяється синхронізація лише платформних ресурсів і залежностей, потрібних для відновлення. GeoNode, Celery, GeoServer та публічні маршрути залишаються вимкненими до імпорту даних. Відновлюються PostGIS, об'єкти, медіа й DATA_DIR з узгодженої точки. Після імпорту запускаються GIS-застосунки з внутрішнім доступом для перевірки прав і тестових шарів. Окремий сценарій відновлення etcd використовує сумісну версію k3s, той самий токен і відновлені PV. В обох сценаріях трафік відкривається після smoke-тестів. Результат вправи — виміряні RPO і RTO та перелік ручних дій.

## Спостережуваність

Prometheus збирає метрики вузла, Kubernetes, ingress, PostGIS і перевірених endpoint застосунків. Grafana має дашборди по вузлу, стану дисків, GIS-запитах і резервуванню. Alertmanager сповіщає про заповнення дисків, недоступні сервіси, помилки синхронізації Argo CD та прострочені копії. Loki працює в monolithic-режимі, Alloy збирає логи контейнерів, а retention і розмір дисків телеметрії обмежені окремо. Для падіння всього GIS-сервера потрібна перевірка поза ним. Початкове місце для неї — вузол MAAS, якщо є незалежний канал доставки сповіщень. [Grafana Loki](https://grafana.com/docs/loki/latest/get-started/)

## Порядок реалізації та приймання

1. Перевірити мережу, диски й NAS. Підтвердити MAAS commissioning і відтворюваний bootstrap на чистій ОС.
2. Підняти Argo CD, ingress, секрети, сховища й моніторинг. Перевірити merge → sync, реакцію на drift та сповіщення про втрату доступу до GIS-вузла.
3. Розгорнути PostGIS і RustFS, перевірити запис і читання. Розгорнути GeoNode з GeoServer, опублікувати тестовий шар, перевірити права й OGC-відповідь. Перевірити MVT від Martin та raster tile від TiTiler.
4. Відновити тестовий набір із NAS на чистому вузлі й повторити GIS-перевірки. Звірити виміряні втрати даних і простій з погодженими цілями до перенесення робочих даних.

Перед реалізацією потрібні фактичні CPU/RAM і диски, мережеві сегменти та BMC, протокол і можливості NAS, профіль доступу, очікуваний обсяг даних і допустимі простій та втрата даних. Версії, requests/limits, retention, брокер, вибір оператора PostGIS і формат копіювання остаточно визначаються за цими вимогами та фіксуються в ADR. Ingress на базі Traefik k3s, cert-manager за потреби автоматизації TLS та Alertmanager з Alloy — початкові пропозиції, які можна уточнити після перевірки середовища.
